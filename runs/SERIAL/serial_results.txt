[6] THE BOUNDARY GUARD  (S8)
==============================================================================================
  word = (n << 2) | k silently corrupts if n can reach 2^30: the top bits of n land in k's
  field.  So the header must reject it.  Tested, not asserted:

  header         outcome   reason                                              
  -------------  --------  ----------------------------------------------------
  M=4, N=2^30-1  ACCEPTED  -                                                   
  M=4, N=2^30    ACCEPTED  -                                                   
  M=4, N=2^30+1  REJECTED  N = 1073741825 exceeds 1073741823: n does not fit in
  M=5, N=1000    REJECTED  M = 5 exceeds 4: k does not fit in 2 bits           

  and the consequence, if the guard were absent:
    n = 2^30, k = 1  ->  word = 1  (uint32 wraps)
    decoding that word returns k = 1, not 1 -- silent corruption, no error raised.

  S8  REFUTED     header rejects N >= 2^30 (silent overflow guarded)
       measured: N = 2^30 -> HeaderError; decode of the wrapped word gives k = 1

  E1  S8 is refuted, and the guard is correct.  My prediction mis-stated the boundary by one.
      n ranges over 0 .. N-1, so N = 2^30 gives n_max = 2^30 - 1, which DOES fit in 30 bits:
      (2^30 - 1) << 2 | 3 = 2^32 - 1 exactly.  The admissible bound is N <= 2^30, not N < 2^30,
      and the guard enforces exactly that.  The spec's wording ('requires n < 2^30') is also
      correct, because it bounds n, not N.

      The demonstration in [6] is therefore VACUOUS: it evaluates n = 2^30, an input the guard
      makes unreachable when N <= 2^30.  It is left in place as the record of the error.  Its
      closing sentence is also a formatting bug -- it compares 1 to 1 and prints 'returns k = 1,
      not 1'.  Neither the vacuity nor the sentence affects the criterion; both are mine.

      Also mine: header_check's message reads 'exceeds 1073741823' while the check fires at
      1073741825.  A message off-by-one, not a threshold off-by-one -- the spec is unchanged
      and the behaviour matches it.  Not repaired, so that this run stays the record.

  E2  S7 is refuted, and the reason is a property of the format worth having.
      I predicted decode ~= encode because 'decode is the same operations reversed'.  It is not:
      ENCODE computes k = p // N and n = p % N -- an integer division per record, ~20-40 cycles.
      DECODE computes k = w & 3 and n = w >> 2 -- two bit operations, ~1 cycle.
      Measured ratio 2.37x in decode's favour.  So the format is deliberately asymmetric: the
      WRITER pays the division once, the READER pays almost nothing.  That is the right way
      round for a 16 GiB file read many times, and it is an argument for the bit-field layout
      that I had not made.

      A7 itself passed: 38.0 s encode / 16.1 s decode against a 1800 s ceiling.  Only the
      'A6 ~= A5' sub-prediction failed.

  E3  S9 was amended before measurement, and the amendment is recorded in the registration.
      The archived raster figure 0.9961 belongs to S = 256 and does not transfer; at S = 4096
      it is 0.999756, measured exactly.  Had I left the original threshold, this run would
      have 'refuted' a correct claim on a scale-transfer error -- the same class as round 27
      P10 and round 28 P11.
