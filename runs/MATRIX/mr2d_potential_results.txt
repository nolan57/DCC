      sIV: 500-1000 voxels.   sV: optimised for 4,279,069,764 voxels.   ratio = 4.179e+06
      at 1024 pieces the entire state is 4.0 kB; bit-packing to 32 bits saves
      0 bytes, because 32 bits is already what 4 bytes means.  Memory mapping saves nothing.
      at 4,279,069,764 pieces the same array is 15.9 GiB.
  P12  sIV and sV describe different problems                       : PASS   ratio 4.18e+06

  the declared bit budget does not close:
      position 6 bits/axis x3 = 18 + normal 3 + material 7 = 28 bits, leaving 4.
      but 6 bits/axis addresses only 64 positions: at 65536 sites per axis you need 16 bits
      per axis = 48 bits for position alone.  A chunked layout needs a chunk index on top:
      64^3-chunks -> 16,324 chunks -> 14 bits index; total = 28 + 14 = 42 bits
  P13b the 32-bit per-vertex claim is 10 bits short                 : PASS   42 bits needed

  P13 the solver claim:
      'CG ... discard Newton, which requires an (3N)^2 Hessian'.
      (a) with the Morse term the objective is NONLINEAR in the coordinates, so plain CG
          (a linear solver) cannot minimise it.  Nonlinear CG can, and is memory-light --
          but then it is a different algorithm from the one named.
      (b) for ARAP alone the global step is a CONSTANT sparse system (all weights and the
          cotangent Laplacian are fixed), so the standard method is ONE prefactored
          Cholesky, then a back-substitution per iteration -- no iterative solve at all.
      (c) a sparse Hessian is not an (3N)^2 dense matrix; sparse Cholesky on a voxel graph
          is the usual approach.  The baseline the comparison rejects is a strawman.
  P13  CG is a linear solver; ARAP's step is constant and prefactorable : PASS   category error + wrong baseline
